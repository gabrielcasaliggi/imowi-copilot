## 1. Target architecture

```text
USER
  ↓
LLM / Interpreter          → intent, proposal, wording (never authority)
  ↓
ActionProposal             → allowlisted commercial/comms intents
  ↓
Policy                     → authorize / deny / require confirmation
  ↓
Conversation Motor         → ConversationState transitions
  ↓
Runtime                    → ActionRequest + TrustedContext → ActionResult
  ↓
Adapter                    → CommercialAdapter | ManagedCommunicationAdapter
  ↓
EXTERNAL AUTHORITY         → BSS/CRM | Communication Authority | Channel Provider
  ↓
Verification               → authoritative READ-back (commercial) / delivery result
  ↓
ActionResult
  ↓
Deterministic Renderer     → customer-safe response
```

| Forbidden call path |
|---|
| LLM → Adapter |
| LLM → External SoT |
| Journey → Adapter (bypass Policy/Runtime) |
| Policy → External Authority (direct) |
| Renderer → External Authority |

**Reuse (do not redesign):** TrustedContext, ConversationState, Policy, Conversation Motor, Runtime, ActionRequest/ActionResult, `confirmation_pending` + `resolve_user_confirmation` pattern, Proactive 2.3 event pipeline (separate domain).

**Do not modify:** Billing 2.1, SM 2.2A–C, Proactive 2.3, CASI, mobile, OV, BillTrack.

## 5. Offer resolution

```text
1. User asks about offer / hire / change
2. Eko identifies commercial intent (LLM may help interpret)
3. External authority supplies offer (catalog/price/promo)
4. Eko renders deterministic offer (facts from authority)
5. User may request eligibility → eligibility authority evaluates
6. Eko presents eligible/ineligible result (authoritative reason_codes)
7. User confirms against OfferSnapshot
8. Runtime → CommercialAdapter → order
9. Status + verify → COMPLETED only if VERIFIED_COMPLETED
```

**LLM may:** interpret intent, propose action, draft wording around authoritative facts.  
**LLM must not:** invent price, discount, eligibility, promotion terms, or declare completion.

---

## 6. Offer snapshot (immutable)

Before confirmation, freeze:

| Snapshot field |
|---|
| `offer_id`, `product_id`, `plan_id`, `promotion_id` |
| `price`, `currency`, `billing_period` |
| `terms`, `validity` (`effective_from` / `effective_to`) |
| eligibility result (+ reason) |
| authority versions (catalog / pricebook / promo / eligibility) |
| `snapshot_id`, `timestamp` |

Confirmation **must** reference `snapshot_id`.

**Invalidate confirmation if any of these change:** price, plan, promotion, eligibility, selected_service_ref, trusted_client_number, operation.

Reuse conceptual pattern: `confirmation_pending` + `resolve_user_confirmation` — **do not activate** for commercial EFFECT until gates pass.

---

## 7. Confirmation gate

Runtime may execute commercial EFFECT **only if all** hold:

1. Ownership valid (TrustedContext)  
2. Offer valid (snapshot vs current authority check or snapshot TTL policy)  
3. Eligibility valid  
4. Price valid (matches snapshot / pricebook version)  
5. Confirmation explicit  
6. Confirmation bound to snapshot  
7. Idempotency present  
8. Authority available  

Any failure → **NO EFFECT** (HANDOFF / DENIED / REQUIRES_INPUT / AUTHORITY_UNAVAILABLE as appropriate).

---

## 8. Idempotency

| Party | Identifiers |
|---|---|
| Eko | `idempotency_key`, `correlation_id` |
| External | `external_transaction_id`, `order_id` |

**Rule:** same `idempotency_key` + same `operation` + same subject → same logical transaction (replay returns prior result).

**Conflict:** reuse with different payload → `DUPLICATE_REQUEST` / `IDEMPOTENCY_CONFLICT` — never a second order.

Contract must define (when authority exists): TTL, replay behavior, duplicate response, conflict behavior. **Today:** NOT_FOUND — do not invent live semantics.

## 9. Verification (post-write)

```text
execute(CommercialRequest)
  → CommercialResult (may be ACCEPTED / PROCESSING / UNKNOWN)
  → get_status(order_id | external_transaction_id | idempotency_key)
  → verify()
```

| `verification_status` | Customer communication |
|---|---|
| `VERIFIED_COMPLETED` | May communicate completion |
| `VERIFIED_PROCESSING` | In progress — not success |
| `VERIFIED_FAILED` / `VERIFIED_CANCELLED` | Failure / cancelled |
| `UNKNOWN` | **Never** success |

Timeout on execute → `UNKNOWN` → mandatory status query.  
**Never** treat timeout / unavailable / unknown as success.

## 10. Commercial error model

| Code | Meaning (summary) |
|---|---|
| `AUTHORITY_UNAVAILABLE` | SoT down / not configured |

| `INVALID_OFFER` / `INVALID_PRODUCT` / `INVALID_PLAN` / `INVALID_PROMOTION` | Bad refs |
| `NOT_ELIGIBLE` | Eligibility failed |
| `PRICE_CHANGED` | Snapshot stale |
| `CONFIRMATION_REQUIRED` | Missing / invalid confirm |
| `IDEMPOTENCY_CONFLICT` | Key reuse conflict |
| `ORDER_REJECTED` / `ORDER_FAILED` / `ORDER_UNKNOWN` | Authority outcomes |
| `VERIFICATION_FAILED` | Post-write check failed |
| `INSTALLATION_REQUIRED` / `INSTALLATION_UNAVAILABLE` | Field work dependency |

Each error → deterministic customer-safe copy + internal audit + **no false success**.

---

## 31. Security model

**Commercial:** TrustedContext → ownership → Policy → Runtime → CommercialAdapter → external authority (service credentials).

**Communication:** authorized_operator → approved content → authorized audience → channel policy → adapter → provider.

**Roles:** AUTHOR · REVIEWER · APPROVER · EXECUTOR · AUDITOR — LLM path must not substitute these.

Least privilege; no cookie reuse; no OV scraping; no session bypass; no credential exposure in logs.
